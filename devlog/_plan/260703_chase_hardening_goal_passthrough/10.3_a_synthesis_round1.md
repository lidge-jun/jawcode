## Findings

### PLANNER-A1 — DuckDuckGo hedge rule ambiguous for longer provider chains

Decision: accept.

The draft said “non-primary DuckDuckGo fallback” but only tested `[slow primary, duckduckgo]`, leaving implementers to infer behavior for `[primary, secondary, duckduckgo]` chains.

Plan changes:

- Cluster D now defines a single hedge rule: schedule exactly one DuckDuckGo hedge when DuckDuckGo appears at any non-zero index; start it while the first non-DDG provider is still running; reuse it only after all pre-DDG providers fail; do not start one hedge per provider.
- Tests now require both the two-provider hedge case and a longer chain `[slow primary, second slow failing provider, duckduckgo]` case.

### PLANNER-A2 — provider timeout rollout lacked a complete checkable callsite assertion

Decision: accept.

The plan listed provider files but tests only asserted helper semantics. A provider file could be missed and still pass behavioral helper tests.

Plan changes:

- Tests now require a static callsite assertion or fixture-backed review test proving every named provider/Kagi callsite uses the required class timeout or documented explicit exception.
- Acceptance explicitly requires API/LLM/Kimi/non-provider timeout classification.

### ARCH-A1 — no-arg `withHardTimeout()` default would silently regress `web/parallel.ts`

Decision: accept with design adjustment.

The draft copied GJC's 300s omitted/default ceiling, but JWC has no-arg `withHardTimeout()` users outside the listed provider directory (`packages/coding-agent/src/web/parallel.ts`). Raising the omitted default would silently lengthen those paths from 60s to 300s.

Plan changes:

- Do not adopt GJC's 300s omitted default in JWC.
- Keep `SEARCH_HARD_TIMEOUT_MS` at the current 60_000 for omitted/no-arg calls.
- Add API/LLM class constants as opt-in only.
- State that non-provider no-arg users such as `web/parallel.ts` retain 60s default.
- Add `web-search-parallel.test.ts` to focused verification.

### ARCH-A2 — Kimi transport timeout underspecified

Decision: accept.

Kimi sends a 30s API budget but currently uses no-arg `withHardTimeout(params.signal)` for transport. It should not inherit any accidental omitted-default behavior and should not use the 15s API class.

Plan changes:

- Kimi now has an explicit transport timeout decision: pass a documented numeric ceiling compatible with its 30s API budget, for example 60_000 matching current JWC behavior.
- Kimi is listed as an allowed explicit-timeout exception in provider callsite assertions.

### ARCH-A3 — format clamp could cap unbounded large values forever

Decision: accept.

The draft described clamping integer B and byte GB bands without constraining that to supported below-next-unit transitions. Applied literally to unbounded branches, very large values could cap forever at `999B` or `1023.9GB`.

Plan changes:

- Acceptance now limits compact-number clamp to supported suffix transitions K→M and M→B; values above supported B preserve current unbounded B behavior unless a later phase adds T suffixes.
- Acceptance similarly limits byte clamp to KB→MB and MB→GB; values above supported GB preserve current unbounded GB behavior unless a later phase adds TB suffixes.

### ARCH-A4 — exposed timeout copy would become stale

Decision: accept.

Changing timeout semantics requires updating user/model-facing text currently advertising uniform fast 60s behavior.

Plan changes:

- Cluster D now requires updating `webSearchSchema` description, `providers/base.ts` parameter descriptions, and `settings-schema.ts` `web_search.timeout` description.

## Residual risk

Search Cluster D remains the riskiest part of Phase 10. The revised plan reduces blast radius by making class timeouts opt-in and keeping no-arg defaults stable. Delta re-audit should focus on timeout dependency graph, hedge rule clarity, and static/provider callsite verification.
