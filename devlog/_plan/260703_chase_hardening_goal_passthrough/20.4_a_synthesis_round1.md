## Architect findings

### ARCH-A1 — custom-tool schema owner mismatch

Finding: Cluster B specified unknown-key rejection by reading raw `parameters.properties` / `optionalProperties`, but real custom tools are Zod or zod-backed TypeBox first. The wrapper must use the canonical wire-schema conversion owner.

Decision: accept.

Local evidence:

- `packages/coding-agent/src/extensibility/custom-tools/types.ts:184-186` documents custom-tool `parameters` as Zod or TypeBox.
- `packages/coding-agent/src/extensibility/typebox.ts:10-15` maps TypeBox compatibility to Zod behavior.
- `packages/ai/src/utils/schema/wire.ts:185-211` exposes `zodToWireSchema()` and `toolWireSchema()` as the canonical provider wire-schema conversion.

Plan changes:

- Cluster B now adds `allowedToolArgKeysFromWireSchema(schema)` instead of raw JTD-only shape assumptions.
- `CustomToolAdapter.execute()` must call `toolWireSchema(this.tool)` from `@jawcode-dev/ai/utils/schema`, then derive allowed keys from the converted JSON Schema.
- Integration tests now require strict Zod object, zod-backed TypeBox object, and raw JSON Schema object coverage.

## Residual risk

- `allowedToolArgKeysFromWireSchema()` should return `null` for non-closed/non-object/combinator schemas rather than guessing. This preserves execution for exotic schemas while still protecting ordinary strict object tools.
- Deferred plugin cache ordering and extension-agent discovery must not be claimed as closed in B/C/D.
