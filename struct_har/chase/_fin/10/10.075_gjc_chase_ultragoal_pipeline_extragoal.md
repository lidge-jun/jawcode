## Why This Is A Gap

GJC's ultragoal work moved beyond the older goal-ledger foundation into pipelined scheduling, aggregate validation batches, stricter receipt freshness, and an external "extragoal" review gate. JWC has a native goal engine and compatibility aliases, but the local design has already collapsed public `ultragoal` into `jwc goal` and `ralplan` into `jwc orchestrate p` / `jwc planphase --write`.

The gap is therefore not "copy ultragoal as a new public mode." The useful upstream behavior is the scheduler/receipt/review discipline. JWC should adapt that into its `jwc-runtime` goal/orchestrate owners while preserving the current public workflow surface.

> **Execution order**: after context/perf and before session/skill/TUI/Telegram in the sequence: model/provider -> context/perf -> session -> skill -> TUI -> Telegram.
> **Sub-card split needed**: yes — split pipeline scheduling, validation batches, receipt freshness, and review-gate/template adaptation if implementation scope grows.
> **Implementation approach**: absorb the useful ultragoal/extragoal behavior into `jwc orchestrate` internals, adapting pipeline and validation-batch semantics inside PABCD `goal-engine.ts` instead of adding a separate ultragoal mode.
> **OPEN ASSUMPTIONS**: status stays open (`⬜`) because runtime implementation is still required; deprecated `ultragoal` remains compatibility-only.

## WP8 implementation triage — 2026-07-11

**Decision: COVERED + focused adaptation.** JWC already pipelines the ordinary durable-goal path through `checkpointAndContinueGoal()` and `startNextGoal()`, emits one goal-ledger checkpoint for each orchestrate transition, requires fresh completion receipts, and provides the extragoal-equivalent external review stop through `record-review-blockers` plus the P/A/C review gates. A new public `ultragoal` or `extragoal` surface remains rejected.

The remaining actionable batch gap was implemented in `jwc-runtime/goal-engine.ts`: `GoalPlan.validationBatch` is additive/read-compatible, malformed or foreign batch metadata is ignored on read, a batch final goal is not schedulable until every non-final member is complete or superseded, and member checkpoints drive the durable batch through pending/running/failed/complete. Existing plans without batch metadata retain their prior scheduling behavior.

Residual note: GJC's speculative overlapping-worker protocol and injected extragoal tools were intentionally not ported. JWC's orchestrate/team permission and actor lifecycle must own any future parallel overlap feature.
